Full Documentation

Inoxity is now a two-repo system: a SwiftUI iOS app participants enroll in with a study code, and a Next.js researcher dashboard where studies are configured. Every study's participant data lives in a Supabase project the research team owns and controls — Inoxity itself only ever routes participants to the right one. This page covers the current architecture, how a study actually gets set up, and how the app behaves at runtime.

Overview

Inoxity is designed for IRB-approved research studies that collect Apple Health data, deliver brief EMA survey prompts, and optionally accept media uploads — all without participants ever creating a traditional account. A participant enters a study code; the app resolves that code through the Control Backend (a single shared Supabase project Inoxity operates) to find which Study Backend — the research team's own, separate Supabase project — that study actually uses. Every participant-facing operation after that point (enrollment, survey events, HealthKit samples, media, withdrawal) goes straight to that Study Backend. The Control Backend never sees participant data — only the routing information needed to find the right destination.

Research teams don't hand-edit configuration files or write SQL by hand: the dashboard's study wizard produces both the study's configuration and the exact setup SQL to paste into their own Supabase project.

Core Features

Wizard-configured studies

Identity, schedule, onboarding, HealthKit, notifications, surveys, reminders, and support content are all set from the dashboard — no hand-edited config file.

Configurable HealthKit sync

Up to 117 HealthKit sample types, chosen per study, plus an optional one-time characteristics snapshot (biological sex, blood type, date of birth, Fitzpatrick skin type, wheelchair use).

EMA random-window scheduling

Surveys can fire at a random time within a configured window rather than a fixed clock time, with per-survey prompt expiration and configurable reminders alongside them.

Flexible participant start dates

A study's schedule can start on enrollment, a fixed calendar date, or a date the participant selects themselves during onboarding.

Real media uploads

Photos and videos upload to the study's own Supabase Storage bucket, with an optional participant-entered "represented date" for what the media depicts.

Withdrawal with genuine deletion

A participant choosing "delete existing data" on withdrawal actually deletes their rows and uploaded files, not just a recorded preference.

App Flow

  1. Participant enters a study code; the app resolves it via the Control Backend to the study's configuration and its Study Backend identity.
  2. An anonymous session is established directly against that Study Backend and verified against the identity the Control Backend returned — a mismatch is treated as untrusted and refused.
  3. Onboarding walks through whatever steps that study actually configured (participant ID entry, HealthKit permission, notification permission, participant-selected start date if enabled, etc.) — not a fixed sequence.
  4. Home shows study information, "See My Data" summaries, and settings, with survey/reminder scheduling reconciled in the background.

Participant progress is persisted locally, versioned, and migrated forward automatically — a participant who already completed onboarding returns directly to the home interface on the next launch.

Data Model And Services

HealthKit sync

An anchored query per configured type backfills recent history on first sync, then only fetches new or changed samples afterward. Each sample carries its own captured IANA time zone alongside its UTC timestamps, read from the sample's own metadata when the source provided it, falling back to the device's current zone.

Notifications & surveys

Survey and reminder notifications are scheduled per the study's configured windows (fixed time or random-window), routed by identifier back to the exact survey occurrence when tapped, and reconciled against the current configuration on every foreground.

Study Backend persistence

Every write — enrollment, survey events, HealthKit samples, characteristics, media, withdrawal — goes through a dedicated Postgres RPC on the study's own Supabase project, bound to the caller's verified identity and the study's own backend instance, never a direct table write.

Local state

Onboarding progress, participant identifier, notification/HealthKit permission state, and sync cursors persist on-device, versioned so a schema change can migrate old saved state forward automatically.

Study Backend Resources

A researcher's own Supabase project — never Inoxity's — holds all of this. The dashboard generates the exact setup SQL for whichever tables a given study actually needs.

Resource Purpose
participants / study_enrollments One row per enrolled participant and their enrollment record, including their own participant identifier.
survey_events Opened/completed events per survey occurrence, each with its own captured local time zone.
Per-HealthKit-type sample tables One dedicated table per configured type (e.g. sleep_samples, step_count_samples) — up to 117 possible, narrowed to what the study actually collects.
participant_characteristics One-time HealthKit characteristics snapshot per participant, when a study opts in.
media_uploads Tracks uploaded files, MIME type, size, and the participant-entered "represented date."
withdrawal_requests Records withdrawal choice and, for "delete existing data," actually removes the participant's rows and Storage files.
user-uploads Storage bucket for participant media files.

Configuration

There's no config file to hand-edit anymore. A study's entire configuration — identity, schedule, onboarding, HealthKit, notifications, surveys, reminders, support content and FAQs, and its Data Backend — is set step by step in the dashboard's study wizard and saved as a versioned configuration record.

  • The wizard's Data Backend step is where a research team points a study at their own Supabase project and generates that project's setup SQL.
  • The Review step validates the whole configuration before it can be saved or activated.
  • A study only starts resolving for real participants once its status is set to Active.
Configuration is versioned (SCHEMA_VERSION). An already-provisioned Study Backend's study_backend_metadata.supported_configuration_schema_version doesn't update itself when that version bumps — see Troubleshooting below.

Setup

  1. In the dashboard, create a study and work through the wizard's steps.
  2. On the Data Backend step, create (or point to) your team's own Supabase project, then copy the generated setup SQL and run it there — never against Inoxity's own Control Backend.
  3. Set the study's status to Active, then activate it from its detail page.
  4. Share the study code with participants.
  5. Build the iOS app with the Inoxity-Production scheme (not the default Development scheme) to test against a real, active study on a real device — HealthKit and notification behavior don't fully work in the simulator.

Troubleshooting

  • If the app reports the study's backend as inactive or mismatched right after setup SQL was applied, check study_backend_metadata.supported_configuration_schema_version matches the study's current SCHEMA_VERSION — this needs a manual SQL update whenever the schema version bumps.
  • If you change a study's configuration (e.g. add a HealthKit type) after its Supabase project is already set up, don't re-run the whole generated setup SQL — its create table statements aren't idempotent and will fail on tables that already exist. Re-download the setup SQL and apply only the new or changed pieces.
  • If HealthKit or notification behavior looks wrong, confirm you built with the Inoxity-Production scheme against a real device and an actually-Active study — the Development scheme and simulator both behave differently.
  • If uploads or sync silently fail, verify the participant's HealthKit/notification permissions and that the Study Backend's RLS policies match the generated setup SQL exactly.
